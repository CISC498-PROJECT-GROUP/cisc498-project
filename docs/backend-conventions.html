Backend conventions

Required reading before any work in backend/. The rules below are enforced by tests/architecture/ where they can be — the rest are on review.

Bun runtime · Hono router · TypeScript strict · tests on the Bun test runner · no database · sessions in memory

01

The layers

src/routes/<module>/ → src/services/<module>/.

Each layer may only reach the one directly below it. src/api/ is not a layer and must never appear. When a database arrives, a src/repositories/ layer goes below services and becomes the only place a query may live.

02

Routes

  • One folder per module: routes/<module>/<module>.ts exporting router_<module>. No naked .ts files at routes/.
  • Routers stay thin — parse, validate, delegate. No business logic.
  • Respond ONLY through rsp(c, data, stc, message) with the stc/err enums — never raw c.json. Every caller parses one envelope: { data, statusCode, message }.
  • Hono-Context helpers live here (a module's common.ts), never in services.
  • Mount every router in src/index.ts.
03

Services

  • services/<module>/ holds the business logic. Feature services never import hono.
  • services/common/svc-*.ts — cross-cutting clients (env, response, log, the model transport).
  • Functional modules — no classes, no DI container.
04

Environment

A new env var goes into EnvKey + app_env + getEnvStatus() in svc-env.ts and .env.example, in the same commit. Read env only through app_env — never process.env.X anywhere else.

A missing credential is a warning, not a crash. The API must still boot and answer /health, so the extension can tell "backend down" from "backend up but not configured".
05

Logging & student data

Log through createLogger(tag) from svc-log.ts: one line per event, [tag] message key=value.

Never log an API key, a student's password, 2FA code, session id or UD cookie, a student's question, anything a UD system returned (Canvas content and lecture transcripts, Stellic records, WebReg schedules), or model output. Counts, statuses, hosts, timings and field names only. Student data is used to answer the question asked and is not stored.
06

Tests

tests/routes/ and tests/services/ mirror the src/ shape exactly. Tests never talk to live infra — stub fetch or the svc-* boundary. tests/architecture/ holds the structural tests (layering, the 200-line limit across the whole repo); they run with everything else.

07

Deployment

The root Dockerfile packages the backend alone; compose.yaml runs it with backend/.env. Bun runs the TypeScript directly — no build step — so the image carries backend/src, packages/shared and the root lockfile and tsconfig. A new file the backend needs at runtime outside backend/src must be added to the Dockerfile's COPY lines. The image installs Chromium (CHROME_PATH) to print study PDFs and fonts-lmodern for their math; without a browser the API still runs and /study/render answers 503.

The container listens on 0.0.0.0, so the port mapping is the only thing keeping it off the network. It stays 127.0.0.1:3010:3010, fronted by whatever serves the site and relays /api/* over HTTPS: this API holds students' live UD sessions and spends the key, and must never be reachable except through the site.
08

Model output is checked

What the model writes for a student to study from is checked before it ships (services/study/):

  • Its shape: structured outputs (output_config.format), then coercion (coerce*.ts). Keep schemas flat — a union of many shapes, or nested lists of them, compiles to a grammar the API refuses as too large.
  • Its quotes: a quote of the instructor must be in the transcript (a digest) or in a transcript-checked digest (a plan, a section); an unmatched one is dropped, never repaired.
  • Its links: a video URL must have come back from that call's web search, or be one the course posts.
  • Its markup: text is escaped; diagram SVG is rebuilt from an allowlist; the page is printed with every network request refused.
09

Students' UD sessions

The site has no login of its own. services/auth/ signs a student into UD once — their username and password typed into CAS's own form in a Chrome window kept off-screen, then UD's 2FA page brought on screen for the student to enter their code in — and the Canvas, Stellic and WebReg sessions that sign-in leaves behind are what services/upstream/ makes every request with.

  • The password is used once. It goes from the request into CAS's form and is dropped. It is never stored, logged, or kept on the session.
  • Sessions live in memory only (sessions.ts): the cookie jar, the student's isolated browser context (kept so a lapsed service can be renewed through CAS single sign-on), nothing else. Sign-out or an hour idle ends one; a restart ends them all. No database, no disk.
  • The site holds only an unguessable session id, in an HttpOnly, SameSite=Strict cookie. Every non-GET must carry X-Requested-With: canvas-assistant. /chat, /study and /up need a signed-in session (routes/auth/common.ts).
  • The proxy is not open. upstream/policy.ts lists the hosts, and on each the only writes allowed: Canvas assignment submissions, WebReg's sisqueue add / drop / swap / edit. A new write is a product decision, made there and in the docs, not a refactor. /up is the one route that answers with the upstream response itself rather than rsp(); its failures still use the envelope.
  • The 2FA code never touches the site. When CAS asks for it — on its own page, or in a popup — login-window.ts brings that window on screen and the student enters the code there; second-factor.ts only notices the page is up. So the backend must run where the student can see its windows: their own machine. CAS is driven by what its pages say (cas.ts); LOGIN_BROWSER_VISIBLE=1 keeps every sign-in window on screen for debugging a change to it.
  • UD_STANDIN fakes the sign-in and sends every UD request to the stand-in (web/preview/) — the only place registration writes may be exercised.
