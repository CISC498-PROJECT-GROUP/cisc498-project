Extension conventions

Required reading before any work in extension/. The extension runs inside someone else's page — Canvas — so most of these rules are about not disturbing it and not being disturbed by it.

Chrome Manifest V3 · Preact + hooks · TypeScript strict · bundled by Bun.build · Shadow DOM

01

Isolation from Canvas

  • Everything renders inside the shadow root created in content.tsx. Never append to Canvas's DOM or read its layout.
  • Keyboard events stop at the widget root (app.tsx). Canvas binds global shortcuts on document; a key typed in our input would otherwise reach them.
  • The content script mounts only where canvas-page.ts allows (the dashboard). Widening that is a product decision, not a refactor.
Content scripts run in an isolated world: the page's window.ENV and scripts are invisible to us. Read Canvas through its REST API, not its globals.
02

Data only through hooks

Components never call fetch, the Canvas API or chrome.*. Every source lives in services/hooks/use-*.ts and returns a Loadable<T> — { data, loading, error }, rendered by <LoadState>.

Canvas calls are same-origin fetch('/api/v1/…') from the content script, which carries the student's session. Calls to our backend go through the extension's background service worker, not the page, so Canvas's CSP and CORS never apply to them.

03

Canvas is the only source of record

Every grade, date and policy the widget or the assistant shows comes from the Canvas API. Invented data exists only as the preview harness's fixtures in extension/preview/, which the build never bundles. The assistant is told to state only what a tool returned, and tool results carry times already in the student's zone (localStamp).

Canvas access is read-only: canvas-api.ts only issues GET. Anything that writes to Canvas (submitting, messaging) is a product decision, not a refactor.
04

Folder layout

  • components/<feature>/ — one folder per view; shell/ is the launcher and panel chrome, common/ the shared pieces.
  • services/hooks/ data · services/types/ view-models · services/format/ pure formatting · services/canvas/ the REST client and mappers · services/tools/ tool executors · services/chat/ the tool loop.
  • A new tool is added to @canvas-assistant/shared first; the executor map in services/tools/index.ts is typed by the shared names, so a missing executor fails to compile.
  • A type both the extension and the API use moves to @canvas-assistant/shared.
  • Pure logic gets a test in extension/tests/.
05

Styling

  • Plain CSS in src/styles/, one file per area, joined by styles/index.ts. Every class is prefixed ca-.
  • Colours come from the tokens in tokens.css — never a hex in a component. A per-course colour is passed as the --ca-course custom property.
  • The accent is var(--ic-brand-primary), the school's Canvas theme colour.
  • Resets use :where() so they carry zero specificity and never beat a component class.
06

Accessibility

Real <button>, <a href> and <input> + <label>; aria-label on icon-only buttons; touch targets at least 40px; Escape closes the panel and returns focus to the launcher; motion respects prefers-reduced-motion.

07

Build, load, preview

  • bun run dev rebuilds extension/dist/ on change. Load that folder via chrome://extensions → Load unpacked; after each rebuild press the reload arrow and refresh Canvas.
  • The bundle is an IIFE — content scripts are classic scripts and cannot contain import.
  • bun run --cwd extension preview serves a stand-in dashboard on :5174 over a fake Canvas API, with chat going to the real backend — the whole tool loop runs without a Canvas login.
