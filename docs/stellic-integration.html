Stellic integration

How the site reads a student's degree plan and audit from UD's Stellic, which has no public API. Read this before touching web/src/services/stellic/. Everything here was worked out by watching UD's own Stellic web app (stellic.udel.edu) in November 2026, with permission from Stellic's technical team and the course instructor.

Django session cookie · CSRF token + Origin check · set by the backend's proxy · reads only

01

How Stellic signs a student in

  • Stellic is a Django app. Signing in goes through UD's SAML identity provider (idp.nss.udel.edu, then CAS + Duo); after it, the browser holds a Django sessionid cookie (SameSite=Lax) and a csrftoken cookie. There are no API keys and no OAuth.
  • The session times out after an hour idle (/auth/getsessioninfo/ reports session_timeout: 3600). Stellic's own app keeps it alive with POST /auth/extendsession/; the site does not need to.
  • A request without a valid session gets a 302 to the IdP, never a 401. The backend's proxy follows redirects itself and treats one to the IdP or CAS as a lapsed session.
A fetch can't sign Stellic in — the IdP answers with an auto-submitting HTML form. So the backend opens Stellic in the student's sign-in browser instead: right after the CAS + Duo sign-in, and again whenever the Stellic session lapses, the browser visits /app/planner, CAS single sign-on answers without a prompt, and the new sessionid goes back into the student's cookie jar (backend/src/services/auth/renew.ts).
02

Why the proxy sets Origin

Stellic's read endpoints that take a body are POSTs, so Django's CSRF middleware runs on them. Replaying one (POST /planner/getstudentprofile/) with the student's cookies gave:

  • token + Origin: https://stellic.udel.edu → 200
  • token, no Origin or Referer → 403 · token + Origin: chrome-extension://… → 403 · token + Origin: https://udel.instructure.com → 403
  • Origin right, no token → 403
  • GET endpoints → 200 with the cookie alone

A browser page can't set Origin or Referer on a fetch — the extension this began as needed a declarativeNetRequest rule for it. The site's requests leave from the backend instead, so backend/src/services/upstream/headers.ts simply sets both to Stellic's own values on every Stellic POST, with X-CSRFToken from the csrftoken cookie in the student's jar.

Those headers go only on requests the proxy makes for a signed-in student, to the Stellic read paths policy.ts lists. Never let the proxy POST elsewhere on Stellic: Django's Origin check is part of what keeps Stellic's writes safe, and the proxy passes it by construction.
03

The endpoints the site reads

  • POST /planner/getstudentplan/ (form: include_grades=true; no username means the signed-in student) — the primary plan: plan_id, programs, and sem_content, every term's courses with grade and registration status. ~56 KB, ~2–3 s.
  • POST /planner/getauditinfo/ (JSON: plan_id, mainaudit: true, req_tree: true, …) — the degree audit: req_tree (programs → requirement groups → courses), audit_data by requirement id (satisfied, progress_data.units_summary, cards_remaining), and student_audit.grades_summary.c_gpa. Up to ~550 KB, ~2 s.
  • POST /planner/getstudentprofile/ (empty form) — standing, school, expected graduation term, advisors, and the username. ~200 KB, ~5–10 s: the slowest call, so it loads alongside the rest and never blocks the plan.
  • GET /planner/plan-review-summary/?student_username=… — whether the plan has been reviewed, and with whom a review is open. Needs the username from the profile.

Stellic's own app also calls POST /planner/getinitdata/ first (~750 KB, ~10 s). The site skips it: the plan call needs no arguments and returns the plan id.

Seen but not used: getplancredits (transfer and exam credit), getmilestonesandcoursesandunitssummary (course and credit totals), getplanwarnings (per-term alerts and holds), getgrades, getprereqchain, searchcourses, /student_notes/search_notes/, /notifications/countunread/, /explore/get_list/.

04

Response quirks

  • Every body starts with )]}', and a newline (a JSON-hijacking guard); parseStellicJson strips it.
  • Failure can be a 200 with {"success": false, "message": {...}}; the client treats that as an error.
  • sem_content is keyed by season first (id 1 fall, 2 winter, 3 spring, 4 summer — confirmed by the term dates) and then by plan year ("1"…"4"). physical_year is the calendar year the term runs in.
  • A course with a grade is finished; is_registered without a grade is current enrollment; neither is planned. registration_status.screen_name gives Stellic's own label ("Enrolled").
  • Program names carry catalog suffixes ("… Minimum Total Credits 2019F", "(17F-current)"); tidyProgramName drops them for display.
05

Limits and risks

  • Undocumented. These are internal endpoints and can change with any Stellic release. Every mapper tolerates missing fields, and every card fails on its own, so a change breaks one card, not the page.
  • One school. Stellic is deployed per institution; the origin lives in web/src/services/school.ts (with UD's Canvas and WebReg) and in the backend's proxy policy and sign-in (backend/src/services/auth/ud-services.ts).
  • Reads only. Nothing writes to Stellic. A write would be a product decision and a conversation with Stellic first, not a refactor.
  • Source of record. The site shows Stellic's figures as Stellic states them — satisfied flags, credit totals, GPA. It adds credits up but computes no GPA or requirement status of its own.
  • Privacy. Stellic data passes through the backend's proxy on its way to the student's page and is neither stored nor logged; the assistant sees it only when its get_degree_plan tool is called to answer a question.
06

Re-discovering an endpoint

Open Stellic in Chrome with DevTools → Network → Fetch/XHR, sign in, and use the screen that shows the data you want; the call it makes is the endpoint. Copy it as cURL to see the body and headers. For a scripted capture, launch Chromium with --remote-debugging-port and record Network.requestWillBeSent / Network.getResponseBody over the DevTools protocol — that is how this page and WebReg integration were written.
