WebReg integration

How the site reads a student's registration from UD's WebReg and changes it on their say-so. WebReg has no public API; everything here was worked out in November 2026 by watching UD's own WebReg page (webreg.nss.udel.edu/registration/schedule/<term>) and reading its scripts (registration/js/schedule.js). Read this before touching web/src/services/webreg/.

Spring session cookie · CSRF token in a meta tag · queued writes, polled · real registration — test on the stand-in only

01

Writes are real registration

  • POST /registration/sisqueue/add enrolls the student — it is the same call as WebReg's own Add button and goes straight to UD's student information system. There is no cart and no undo; a drop is a second, separate change, and a seat given up may not come back.
  • The site makes a write only after the student has seen the exact change (every section, credits, grading) in a confirm dialog and pressed the button. The assistant never writes — its WebReg tool reads only.
  • The backend's proxy allows exactly four write paths on WebReg (backend/src/services/upstream/policy.ts): sisqueue/add, drop, swap, edit.
Never exercise a write against a real account. bun run preview runs the site against the stand-in UD (web/preview/webreg/), where add, drop and swap change only invented data in memory.
02

Session and CSRF

  • WebReg is a Java (Spring) app behind UD's CAS: /registration/ redirects to cas.nss.udel.edu, and with a live CAS session straight back with a ticket. The backend's sign-in opens it this way after Canvas; a lapsed WebReg session is renewed the same way.
  • Writes need Spring Security's token: <meta name="_csrf" content="…"> and <meta name="_csrf_header" content="X-CSRF-TOKEN"> on every page. The proxy reads it off each WebReg page it relays and sends it as X-CSRF-TOKEN; with none known it reads /registration/ first.
  • The term is session state. Visiting /registration/schedule/<strm> makes that term current, and sisqueue/* act on the current term. The client therefore loads the term's schedule page right before every write.
  • WebReg's own page pings GET /registration/keepAlive while open; the site doesn't need to.
03

Reading: terms, schedule, search

  • GET /registration/schedule/<strm> (HTML) — the page itself carries the data, as inline script: var schedule = [...] (the registered sections), var term = {...} (dates and windows), var maxCredits, var totalCredits, var readOnly, var isAddPossible, var swapOnly. The terms the student may open are the options of <select id="term"> (value = strm, text = "2027 Spring Semester"). /registration/ redirects to the current term.
  • GET /registration/lookupCourses/<strm>/<prefix> — search as you type. A subject or partial course (CISC1) lists courses ({label: "CISC108: INTRO TO COMPUTER SCIENCE I", value: "CISC108"}); a whole course (CISC108) lists its sections ({label: "CISC108010 (Open Seats)", value: "CISC108010"}; labs end in L). Items are under object.items.
  • GET /registration/lookupCourseInfo/<strm>/<section> — one section: meeting times (calendar), instructors, credits (creditOpt), grading options, full, waitlistPossible, waitlistTotal, required components (components: [{type: "LAB", optional: false}]) and the sections that satisfy them (assoc.LAB), notes, longDescr, status.
  • GET /registration/check/<section> — the corequisites dropping this section would also drop (object.corequisites). WebReg calls it before a drop.
  • GET /CoursesSearch/ is UD's public course search page; the site doesn't use it.
04

Writing: add, drop, swap, edit

  • Every write is JSON, Content-Type: application/json, and is queued: the answer is {queueId, nextPollTime}. Poll GET /registration/sisqueue/poll?queueId=… every nextPollTime ms until object.complete; then object.results says what happened (successful, results: {section: bool}, messages, errors) and object.schedule is the schedule afterwards.
  • add: {courses: ["CISC108010", "CISC108020L"], options: [{chosenInstructor: null, creditHr: "3", gradeOption: "SG"}, {chosenInstructor: null, creditHr: 0, gradeOption: "NON"}], overrides: [], waitlist: false} — one option per course, in order. A lecture and its required lab are added together. waitlist: true when a section is full and waitlisting is possible.
  • drop: {courses: [...], withdraw: false, overrides: []} — withdraw is true when the section is past drop and withdrawable.
  • swap: {coursesIn, options, coursesOut, overrides, component} — drop and add in one step, so the seat held isn't lost if the add fails.
  • edit: {courses, options} — change credits or grading on a registered section.
05

Shapes and quirks

  • Every JSON answer is an envelope: {result: "SUCCESS" | …, messages, errors, object}. Anything but SUCCESS is a failure; its errors say why.
  • A section id is subject + number + section, no spaces: CISC108010, lab CISC108020L. The site shows it as "CISC 108-010".
  • A meeting (calendar[]): days: ["T", "R"] (M T W R F S U), startTime: [15, 55] and endTime: [17, 15] as [hour, minute] in 24-hour time, startDate/endDate as MM/DD/YYYY, location often empty before the term. Online sections have no calendar.
  • term times are epoch ms: sessions[].openEnrollment, addWithAppointment, endDropAdd; flags isOpenEnrollment, isAppointmentPeriod, isPenaltyPeriod, isWithdrawPeriod.
  • Grade option values: SG standard, PFS pass/fail, AUD audit; NON for a component with no grade of its own.
  • A course the student took before adds with the message "Course previously taken and may be subject to institutional repeat policy." — success with a warning, shown to the student.
06

Limits and risks

  • Undocumented. These are WebReg's internal endpoints; a release can change them. The mappers tolerate missing fields, and a write's result is read from WebReg's own answer — the site never assumes a change happened.
  • Source of record. The site shows WebReg's schedule as WebReg states it. A planned schedule the student builds on the site is a draft in their browser until they register it.
  • Privacy. WebReg data goes from WebReg to the student's page through the backend's proxy and is not stored or logged; the assistant sees it only when it calls its WebReg tool to answer a question.
